QUY TRÌNH PHÁT TRIỂN PHẦN MỀM (SDLC) & ĐẢM BẢO CHẤT LƯỢNG (QA/QC)

Chuẩn hóa toàn diện từ khâu đặc tả tính năng (Feature Specs), phác thảo giao diện (Mockup), lập kế hoạch Sprint, quy chuẩn đặt tên Commit, ma trận Test Cases, phân định vai trò QA/QC, quy trình Code Review và xuất báo cáo phát hành (Release Report).

🌐 1. Vòng Đời Phát Triển Phần Mềm Khép Kín (SDLC Workflow)

Mỗi tính năng trong đồ án Quản Lý Quán Ăn được vận hành theo chu trình khép kín 7 giai đoạn nghiêm ngặt, đảm bảo tính ổn định và tính minh bạch 100%:

[1. FEATURES & SPEC] ➔ Bóc tách nghiệp vụ (Use Case) + Thiết kế DTO/DAO/BUS + CSDL liên quan │ ▼ [2. MOCKUP & UI] ➔ Phác thảo bố cục Form, co giãn Anchor/Dock, màu sắc nhận diện bàn ăn │ ▼ [3. SPRINT PLANNING] ➔ Lập kế hoạch Sprint 5 bước, định nghĩa Definition of Done (DoD) │ ▼ [4. CODE & COMMIT] ➔ Lập trình theo chuẩn 3-Tier + Tuân thủ Git Conventional Commits │ ▼ [5. QA / QC TESTING] ➔ Viết Test Cases, chạy Unit Test, Integration Test (Order ➔ Bếp ➔ Thu ngân) │ ▼ [6. CODE REVIEW] ➔ Rà soát mã nguồn (SQL Injection check, Package-by-Feature audit) │ ▼ [7. RELEASE REPORT] ➔ Xuất báo cáo HTML độc lập Before/After + Nghiệm thu bàn giao

📝 2. Phân Rã Features & Đặc Tả Kỹ Thuật (Spec)

Toàn bộ tài liệu tính năng được đặt tại thư mục docs/features//. Trước khi gõ bất kỳ dòng code nào, nhà phát triển phải hoàn thành tài liệu đặc tả gồm 3 phần:

1. Đặc Tả Nghiệp Vụ (Business)

- User Stories: "Là [Vai trò], tôi muốn [Hành động] để [Mục đích]".
- Quy tắc kinh doanh (Rules): Ràng buộc số lượng > 0, kiểm tra tồn kho cờ MA_HetMon, kiểm tra trùng số bàn.
- Ma trận phân quyền: Xác định mã Q_Tag tương ứng.

2. Đặc Tả Kỹ Thuật (Technical)

- DTO: Định nghĩa thuộc tính, kiểu dữ liệu khớp 100% cột CSDL.
- DAO: Viết trước các câu truy vấn T-SQL kèm tham số SqlParameter.
- BUS: Quy định các hàm kiểm tra hợp lệ và xử lý logic trước khi gọi DAO.

3. Vòng Đời Form (UI Lifecycle)

- Form_Load: Gọi PhanQuyenHelper.ApDungPhanQuyen(Me), nạp danh sách dữ liệu ban đầu.
- Action Events: Bắt sự kiện Click, CellClick DataGridView.
- Form_FormClosing: Xác nhận lưu vết hoặc dọn dẹp biến bộ nhớ.

🏃 4. Lập Kế Hoạch Sprint & Quy Trình 5 Bước Chuẩn

Để đảm bảo tính nhất quán của kiến trúc Package-by-Feature, mỗi Sprint triển khai tính năng bắt buộc phải trải qua đúng 5 bước tuần tự:

Bước Tên Giai Đoạn Công Việc Cụ Thể (Actions) Sản Phẩm Đầu Ra (Artifacts)
1 Database & DTO Kiểm tra bảng CSDL trong create-database.sql; tạo file XxxDTO.vb khai báo thuộc tính và hàm khởi tạo. XxxDTO.vb
2 Data Access (DAO) Viết các hàm gọi KetNoiCSDL, đóng gói 100% tham số vào SqlParameter; trả về DataTable hoặc danh sách DTO. XxxDAO.vb
3 Business Logic (BUS) Viết lớp kiểm tra dữ liệu đầu vào (không rỗng, số hợp lệ, kiểm tra trùng), xử lý tính toán tiền hoặc chuyển đổi trạng thái trước khi gọi DAO. XxxBUS.vb
4 Giao Diện GUI & Tag Kéo thả control trên Windows Forms, gắn thuộc tính Tag = "Q_TAG" lên các Button cần bảo vệ; gọi PhanQuyenHelper ở Form_Load. frmXxx.vb, .Designer.vb
5 Test & Tích Hợp Chạy thử nghiệm theo Test Cases, kiểm thử phân quyền 4 vai trò, kiểm thử luồng dữ liệu và nghiệm thu Sprint. Biên bản Test & Release Report

🌿 5. Quy Chuẩn Commit Git (Git Conventional Commits)

Dự án áp dụng chuẩn Conventional Commits quốc tế để lịch sử commit rõ ràng, minh bạch và tự động hóa việc xuất báo cáo phát hành:

# Cú pháp thông điệp commit chuẩn: <type>(<scope>): <mô tả ngắn gọn bằng tiếng Việt có dấu hoặc tiếng Anh> # Ví dụ thực tế trong dự án: feat(auth): thêm màn hình đổi mật khẩu và nạp danh sách quyền RBAC fix(pos): sửa lỗi tính sai tổng tiền khi gộp 2 hóa đơn bàn ăn ui(bep): làm nổi bật món ăn có ghi chú đặc biệt trên hàng đợi refactor(core): tách lớp PhanQuyenHelper thành tiện ích quét Control độc lập docs(report): thêm báo cáo phát hành phiên bản release v0.2.8 test(staff): bổ sung test case kiểm tra nhập trùng mã căn cước công dân chore(docker): cập nhật script nạp dữ liệu mẫu seed-data.sql
Tiền Tố (Prefix) Ý Nghĩa Khi Nào Áp Dụng Trong Dự Án Quản Lý Quán Ăn
feat Tính năng mới Thêm Form mới, thêm chức năng gọi món, chuyển bàn, chấm công, in hóa đơn...
fix Sửa lỗi Sửa lỗi văng ứng dụng (NullReference), lỗi SQL Injection, lỗi hiển thị sai màu bàn...
ui / style Giao diện Chỉnh sửa màu sắc, icon, font chữ, bố cục co giãn (Anchor/Dock) trên Form.
refactor Tái cấu trúc Tối ưu hóa mã nguồn, gom nhóm thư mục Package-by-Feature nhưng không đổi chức năng.
test Kiểm thử Thêm kịch bản test case, cập nhật file log kiểm thử tự động.
docs Tài liệu Cập nhật README, tài liệu kiến trúc CSDL hoặc các file HTML báo cáo.

🧪 6. Đảm Bảo Chất Lượng QA/QC & Thiết Kế Test Cases

1 Phân Định Rõ Ràng Vai Trò QA vs QC Trong Dự Án

🛡️ QA (Quality Assurance) — Kiểm Soát Quy Trình Process-Oriented

- Trọng tâm: Ngăn ngừa lỗi ngay từ đầu thông qua quy chuẩn.
- Nhiệm vụ:
• Đảm bảo mã nguồn tuân thủ 100% kiến trúc Package-by-Feature & 3-Tier.
• Đảm bảo 100% câu lệnh SQL có tham số phải dùng SqlParameter.
• Kiểm tra mọi Form có gọi PhanQuyenHelper và gắn mã Tag hợp lệ.
• Đảm bảo script Docker luôn có cơ chế phòng vệ IF NOT EXISTS.

🔍 QC (Quality Control) — Kiểm Thử Sản Phẩm Product-Oriented

- Trọng tâm: Phát hiện lỗi trực tiếp trên phần mềm thực tế.
- Nhiệm vụ:
• Thiết kế bộ kịch bản kiểm thử (Test Cases) chi tiết cho từng phân hệ.
• Thực thi test: nhập dữ liệu biên, dữ liệu âm, chuỗi tiếng Việt có dấu, ký tự SQL lạ (' OR '1'='1).
• Ghi nhận lỗi (Defect Log), phân loại mức độ nghiêm trọng và yêu cầu dev sửa chữa.

3 Ba Cấp Độ Kiểm Thử Thực Tế (Testing Levels)

1. Unit Testing (Đơn vị)

- Kiểm tra hàm băm MaHoaMD5 có xuất đúng chuỗi hash chuẩn.
- Kiểm tra hàm tính tiền trong BanAnBUS (tổng tiền = đơn giá x số lượng - giảm giá).
- Kiểm tra kiểm tra rỗng các trường bắt buộc của NhanVienBUS.

2. Integration Testing (Tích hợp)

- Luồng Order - Bếp - Thu ngân: Phục vụ gọi món ➔ Bếp nhận dữ liệu thời gian thực ➔ Bếp bấm xong ➔ Thu ngân hiển thị đúng hóa đơn và cập nhật trạng thái bàn.

3. UI & Security Testing (UAT)

- Kiểm tra độ sắc nét giao diện trên các độ phân giải màn hình khác nhau.
- Thử nghiệm các kịch bản phân quyền chéo để đảm bảo nhân viên không thể thao tác các chức năng của Quản lý hoặc Chủ quán.

🔍 7. Quy Trình Code Review & Báo Cáo Release Report

1 Bảng Checklist 5 Tiêu Chí Bắt Buộc Khi Code Review

Mọi Pull Request hoặc đợt nộp code đều phải được rà soát đối chiếu với 5 tiêu chuẩn kỹ thuật sau:
  1. Kiến Trúc Package-by-Feature: File mã nguồn có nằm đúng thư mục màn hình tương ứng không?
  2. Không Viết SQL Trong Form: Có câu lệnh SELECT, INSERT nào nằm lẫn trong file GUI .vb không? (Nếu có ➔ Từ chối duyệt).
  3. An Toàn Tham Số (SQL Injection): Toàn bộ tham số truyền vào database có bọc trong SqlParameter không?
  4. Phân Quyền RBAC: Các nút chức năng mới có được gán thuộc tính Tag = "Q_TAG" và nạp danh sách quyền trong Session không?
  5. Bảo Toàn CSDL: Script CSDL mới có dùng IF NOT EXISTS để không làm mất dữ liệu hiện có khi khởi động Docker không?

2 Chuẩn Báo Cáo Phát Hành Trực Quan (Release Report Before/After)

Mỗi khi release một phiên bản, dự án tự động sinh ra một file HTML độc lập tại docs/release_report/report_<version>.html (đã có từ bản report_0_2_0.html đến report_0_2_8.html). Báo cáo bao gồm:

📊 So Sánh Trực Quan Before / After

- TRƯỚC (Before): Trạng thái màn hình cũ, lỗi phát sinh hoặc chức năng chưa hỗ trợ.
- SAU (After): Giao diện WinForms mới (mô phỏng CSS thuần), giải thuật xử lý mới và tính năng được nghiệm thu.

💻 Code Diff Block & Số Liệu Git

- Hiển thị trực quan các dòng mã thêm mới (+ xanh) và dòng loại bỏ (- đỏ).
- Thống kê chi tiết số commit, số lượng file thay đổi và phân loại theo Badge (Feature, Fix, UI, Refactor).
